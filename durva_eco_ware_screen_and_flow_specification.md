# 4. Manufacturing Flow Screen

## Screen: Manufacturing Flow

This screen is represented in the storyboard as a horizontal business-process diagram.

### Purpose

Provide the user with a visual understanding of the manufacturing lifecycle.

### Visible flow

```text
Raw Material Receipt
        ↓
Raw Material Stock
        ↓
Manufacturing / Production
        ↓
Finished Goods
        ↓
Sales & Dispatch
```

### User actions

- Select a stage.
- Navigate to the relevant module.
- View pending operations associated with the stage.

### Business rule

The stages are logically connected. A downstream operation should normally use data generated by the upstream operation.

Example:

```text
Received Material
    → becomes available stock
    → stock is consumed by production
    → production creates finished goods
    → finished goods become available for sale
    → sale creates dispatch requirement
```

# 24. Critical Architectural Rule

The UI should **never directly calculate or mutate authoritative inventory state**.

Recommended flow:

```text
Flutter Screen
      ↓
State Management
      ↓
Repository
      ↓
API
      ↓
Backend Business Logic
      ↓
Database / Inventory Transaction
      ↓
Updated State
      ↓
Flutter UI
```

For example, dispatch should not simply execute:

```text
stock = stock - dispatchQuantity
```

inside the Flutter screen.

Instead:

```text
Dispatch Confirmation
      ↓
Backend Transaction
      ↓
Validate Available Stock
      ↓
Create Dispatch
      ↓
Create Stock Movement
      ↓
Update Stock
      ↓
Return Result
```

# 25. Audit & Traceability

Manufacturing and inventory operations should be traceable.

Important entities should retain:

- Created by
- Created at
- Updated by
- Updated at
- Status
- Reference number
- Related transaction
- Adjustment reason where applicable

A stock movement should be traceable back to its source:

```text
Stock Movement
      ↓
Source Type
      ↓
Source ID
      ↓
Purchase / Production / Dispatch / Adjustment
```

# 32. Recommended Next Step

Before implementing any feature, create the **technical architecture specification** from this screen specification.

The next documentation layer should define:

```text
UI Screen
    ↓
Flutter Route
    ↓
Screen Widget
    ↓
State Provider / Controller
    ↓
Repository
    ↓
API Service
    ↓
Request Model
    ↓
API Endpoint
    ↓
Backend
    ↓
Response Model
    ↓
State Update
    ↓
UI
```

For every screen, the implementation specification should then contain:

- Flutter file path
- Route
- Widget name
- State/provider name
- Repository method
- API endpoint
- Request model
- Response model
- Validation rules
- Loading/error/success states
- Navigation
- Permission requirements
- Related screens
- Test cases

This separation keeps the **UI storyboard**, **business flow**, and **technical implementation architecture** clear and maintainable.
